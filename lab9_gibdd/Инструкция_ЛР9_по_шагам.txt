Шаг 2. Проверь сервер и права root
Открой MySQL Workbench и своё административное соединение, обычно root. Выполни 00_preflight.sql целиком. Требуется MySQL 8.0 с поддержкой ролей, база gibdd и права создавать пользователей, роли и выдавать привилегии. На исходном наборе строки: citizens=10, cars=10, accidents=5, accident_cars=10, sales=5.
Выборка User LIKE 'lr9\_%' при первом запуске должна быть пустой. Если имена уже есть, остановись: CREATE USER не нужно запускать поверх неизвестных аккаунтов. Не удаляй root и не меняй его пароль. При повторной установке сначала установи, что аккаунты действительно созданы только тобой для этой работы; затем по необходимости используй отдельный 99_optional_cleanup.sql и начни установку заново.
Если gibdd отсутствует, исходный дамп есть в lab4_gibdd/04_gibdd_dump_tested.sql этого репозитория. Он пересоздаёт таблицы: импортируй его только в отдельную пустую учебную базу либо после резервного копирования. При наличии рабочей gibdd повторный импорт не нужен. Работы №6–8 заново запускать не требуется.

Шаг 3. Создай пользователей и роли
Под root открой 01_create_accounts.sql. Он содержит учебные пароли с префиксом LR9; эти строки опубликованы в комплекте. Для реального или доступного другим людям сервера замени их собственными сильными паролями до выполнения. Запомни три рабочих пароля: далее они нужны для отдельных подключений. Не включай свои реальные пароли в скриншоты и не сохраняй их в публичный отчёт.
Выполни файл целиком. Создаются lr9_admin, lr9_analyst, lr9_inspector с Host=localhost, а также lr9_demo и lr9_empty с ACCOUNT LOCK. Два последних не используются для входа. Роли созданы с Host=%: это часть имени роли, а не разрешение сетевого входа. Пользователи и роли — разные сущности в модели доступа, хотя роли также отображаются в mysql.user как заблокированные аккаунты.
Если CREATE USER дал ошибку 1396, не продолжай выдачу прав наугад: имя уже занято или предыдущая установка выполнена частично. Проверь 00_preflight.sql. Не добавляй DROP USER в начало установочного файла вслепую.

Шаг 4. Назначь права и роли
Оставаясь под root, выполни 02_grant_roles.sql целиком. Администратор получает ALL только на gibdd.*, аналитик и инспектор — общую роль чтения трёх таблиц. Инспектор дополнительно получает INSERT и UPDATE на accidents и accident_cars. DELETE ему не выдаётся. Глобальных прав на *.* у рабочих пользователей нет.
SET DEFAULT ROLE задаёт активные роли для нового входа. Новые подключения пользователей создавай ПОСЛЕ этого шага. Если подключение уже открыто, переподключись либо выполни SET ROLE DEFAULT внутри него. Не проверяй доступ под root: у него другие права.
CREATE USER, GRANT, REVOKE и SET DEFAULT ROLE не следует оборачивать в тестовый ROLLBACK: управление аккаунтами не является откатываемым изменением обычных записей. Снятие прав выполняется REVOKE, удаление аккаунта — DROP USER. FLUSH PRIVILEGES после штатных команд не требуется.

Шаг 5. Пользователи и права — рисунки 2, 3 и 4
Открой 03_audit_users_roles.sql под root. Выполняй запросы отдельными блоками.
Рисунок 2: первый SELECT из mysql.user. Покажи созданные аккаунты, роли, Host, блокировку и глобальные флаги. Ожидается семь строк: пять пользователей и две роли. Глобальные флаги N допустимы даже у администратора gibdd: права роли на одну базу хранятся отдельно.
Рисунок 3: три SHOW GRANTS ... USING. Запусти каждую команду отдельно и сохрани результат соответствующего пользователя. Можно расположить три снимка под одной подписью рисунка 3. Должны быть видны ALL на gibdd.* у администратора, SELECT трёх таблиц у аналитика, SELECT и INSERT/UPDATE двух таблиц у инспектора. USING раскрывает права роли; не убирай его.
Рисунок 4: запрос списка ролей и запрос mysql.default_roles. Ожидается одна строка назначения lr9_role_admin → lr9_admin и две для lr9_role_reader → lr9_analyst/lr9_inspector. Дополнительно покажи default_roles. WITH ADMIN OPTION у администратора относится к передаче роли, WITH GRANT OPTION — к передаче привилегий.
В методичке встречается SELECT * FROM mysql.user. Он содержит authentication_string, поэтому в отчёте использована выборка полей из той же таблицы без данных аутентификации. Не публикуй хеши паролей.

Шаг 7. Создай отдельные соединения Workbench
На стартовой странице Workbench нажми «+» рядом с MySQL Connections. Создай три подключения: LR9 Admin, LR9 Analyst, LR9 Inspector. Адрес и порт скопируй из своего локального административного подключения; Username замени соответственно на lr9_admin, lr9_analyst и lr9_inspector. Укажи пароли из шага 3. Test Connection → OK.
Аккаунты созданы как @localhost для локального сервера. Если сервер на другом компьютере, Host аккаунта должен соответствовать месту подключения к серверу; имя роли с % не решает эту задачу. Не выдавай всем аккаунтам Host=% вместо диагностики.
В каждом соединении сначала выполни SELECT CURRENT_USER(),CURRENT_ROLE();. Ожидается правильный пользователь и нужная роль. Если CURRENT_USER() показывает root, это не тест созданного аккаунта. Default Schema можно задать gibdd или выполнить USE gibdd.

Шаг 8. Консоль аналитика — рисунки 5 и 6
Открой обычный терминал Windows/Linux. Нужен mysql — консольный клиент, а не SQL-вкладка Workbench. Введи: mysql -u lr9_analyst -p. После приглашения Enter password введи пароль аналитика: символы при вводе не отображаются. Адрес сервера по умолчанию локальный; при необходимости добавь -h localhost и нужный -P порт.
Если команда mysql не найдена, найди mysql.exe в папке bin установленного MySQL Server и запусти по полному пути. Пример Windows: "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -u lr9_analyst -p. Путь зависит от установки.
После появления приглашения mysql> выполни команды файла 04_analyst_tests.sql по частям: USE gibdd; SELECT USER(),CURRENT_USER(),CURRENT_ROLE(); затем SELECT accidentId,accidentDate FROM accidents ORDER BY accidentId LIMIT 5;. Для рисунка 5 должны быть видны консоль, личность аналитика, активная роль reader и пять ДТП.
Затем отдельно выполни UPDATE cars SET price=price WHERE carId=1;. Для рисунка 6 сними команду и ERROR 1142: UPDATE command denied. Это ожидаемый отказ, не сбой установки. Если команда выполнилась без ошибки, проверь CURRENT_USER() и SHOW GRANTS: вероятно, открыто другое соединение или выданы лишние права. price=price не меняет данные даже в таком случае. Выход из клиента — quit.

Шаг 9. Инспектор — рисунки 7 и 8
В Workbench открой именно LR9 Inspector. Открой 05_inspector_tests.sql. Выполни USE и проверку CURRENT_USER()/CURRENT_ROLE().
Рисунок 7A: выдели блок от START TRANSACTION до первого SELECT включительно. Должно создаться временное ДТП с датой 2025-11-01 и city=LR9_TEST. Сделай скриншот полученной строки ДО выполнения отката. Id запоминается в @lr9_accident_id через LAST_INSERT_ID() и может отличаться от примера протокола.
Рисунок 7B: отдельно выполни ROLLBACK и следующий SELECT. Ожидается rows_after_rollback=0. Сними его отдельно и размести оба результата под рисунком 7 с обозначениями «до отката / после отката». Не запускай весь файл одной молнией до снятия промежуточной строки — иначе увидишь только последнюю вкладку результата.
Рисунок 8: выполни только DELETE с accidentId=-1 AND carId=-1. Ожидается Error 1142: DELETE command denied в Action Output. Ключ специально отсутствует: данные не будут удалены даже при ошибке выдачи прав. Но право DELETE сервер проверяет до поиска строк. «0 rows affected» без ошибки не подтверждает запрет. Ошибка 1644 last participant тоже не подходит: она относится к триггеру, а здесь нужно показать именно отказ привилегий 1142.

Шаг 10. Администратор gibdd — рисунок 9
Открой LR9 Admin и 06_admin_tests.sql. Сначала выполни блок до DROP TEMPORARY TABLE включительно. На рисунке 9A покажи CURRENT_USER()=lr9_admin@localhost, активную роль admin, структуру временной таблицы id/note и строку 1, LR9 admin check. Для нескольких Result Grid можно сделать несколько снимков под одной подписью.
Временная таблица существует только в этом соединении и удаляется командой DROP TEMPORARY TABLE либо при закрытии сеанса. Имена исходных таблиц не используются. Не заменяй TEMPORARY на обычную CREATE TABLE. Владельцу временной таблицы дальнейшие действия с ней разрешены на время сеанса; весь набор прав роли подтверждён отдельно через SHOW GRANTS.
Затем отдельно выполни SELECT User,Host FROM mysql.user LIMIT 1;. Рисунок 9B — ожидаемая ошибка 1142. Она показывает, что администратор одной базы не имеет прав root на системную базу. Если выполнить весь файл, Workbench может остановиться на этой последней ожидаемой ошибке; временная таблица к этому моменту уже удалена.

Шаг 11. Все глобальные права и отзыв — рисунок 10
Вернись в соединение ROOT. Открой 07_demo_global_all.sql. Этот файл предназначен только для локального учебного сервера и заблокированной lr9_demo. Никогда не меняй имя получателя на root, lr9_admin или реального пользователя. На рабочем сервере такое упражнение не выполняют.
Сначала выполни GRANT ALL ... ON *.*, SHOW GRANTS и SELECT account_locked. Сними выданные права и блокировку Y для рисунка 10A. Список длинный: в Result Grid включи Wrap Cell Content, увеличь высоту строки и область результатов. Затем ОБЯЗАТЕЛЬНО выполни REVOKE ALL PRIVILEGES ON *.* и SHOW GRANTS: должен остаться USAGE, это рисунок 10B. Не оставляй упражнение на середине.
Аккаунт заблокирован с момента создания, поэтому войти под ним нельзя ни до выдачи, ни после. ALL на *.* относится ко всему серверу; ALL на gibdd.* — только к выбранной базе. После завершения этого шага глобальные права сняты.

Шаг 12. Администрирование в консоли root — рисунок 11
Открой отдельный консольный клиент командой mysql -u root -p и введи свой пароль root. Не выводи и не передавай его в отчёт. Выполни команды 08_demo_usage.sql в этом клиенте. Можно вставить их вручную либо использовать SOURCE полный_путь/08_demo_usage.sql; с настоящим путём к файлу. Например, при распаковке в C:\lr9: SOURCE C:/lr9/08_demo_usage.sql;.
Сначала SHOW GRANTS для lr9_empty показывает USAGE. После GRANT USAGE ... WITH GRANT OPTION появляется возможность делегирования. После REVOKE GRANT OPTION снова остаётся USAGE. Сними три результата или как минимум состояние с GRANT OPTION и после его отзыва для рисунка 11. Это административное упражнение, выполняемое через консольный клиент, в дополнение к операциям Workbench.
USAGE само по себе не даёт доступа к данным. WITH GRANT OPTION — отдельное полномочие, поэтому запись «USAGE WITH GRANT OPTION» нельзя описывать как полное отсутствие любых привилегий. Вход lr9_empty остаётся заблокированным.

Шаг 13. Выборочные глобальные права — рисунок 12
Под ROOT открой 09_demo_selective_revoke.sql. Выполни GRANT SELECT,INSERT,UPDATE,DELETE,CREATE,ALTER,DROP ON *.* TO lr9_demo WITH GRANT OPTION и SHOW GRANTS. Сними результат для рисунка 12A.
Затем выполни оставшиеся REVOKE и SHOW GRANTS в порядке файла. Итог — только USAGE. Если возникли ошибки
1045 Access denied при входе: проверь логин, пароль и Host аккаунта. Сообщение при входе отличается от запрета отдельной SQL-команды после успешного подключения.
1142 command denied в отрицательных тестах — ожидаемый результат. В положительном тесте сначала проверь CURRENT_USER(), CURRENT_ROLE() и SHOW GRANTS под root. Назначенная роль должна быть активна. Переподключение после SET DEFAULT ROLE обычно устраняет проблему неактивной роли.
1396 Operation CREATE USER failed: аккаунт уже существует или установка частично выполнена. Сначала выясни принадлежность имён; не удаляй их автоматически.
1064 возле CREATE ROLE/SET DEFAULT ROLE: проверь, что это MySQL 8.0, а не MySQL 5.7 или MariaDB с другим синтаксисом.
1410/1227 при выдаче прав: у текущего администратора недостаточно полномочий для упражнения. Такие команды должен выполнять администратор учебного сервера. Комплект не меняет конфигурацию или пароль root.
1644 при вставке инспектора: сработало правило из №8. Проверь дату сервера и текст INSERT: используется прошедшая дата 2025-11-01. Это не отказ привилегий.
Пароль отклонён политикой validate_password: выбери собственный более сильный пароль и используй его в подключениях. Не отключай политику ради образца.
Длинный SHOW GRANTS не помещается: включи Wrap Cell Content в Result Grid, увеличь высоту строки, при необходимости сними несколько частей без потери имени аккаунта.

Короткие ответы для защиты
В MySQL 8.0 GRANT не создаёт пользователя: сначала нужен CREATE USER. Аккаунт — это User@Host. Привилегия разрешает операцию на указанном уровне: *.* — весь сервер, gibdd.* — база, gibdd.accidents — таблица. GRANT ALL не включает GRANT OPTION автоматически; ALL на одну базу не даёт глобальный CREATE USER.
Роль объединяет привилегии, назначается пользователю и должна быть активирована. SET DEFAULT ROLE включает её при новом входе, SET ROLE меняет набор активных ролей текущего соединения. WITH ADMIN OPTION позволяет передавать роль, WITH GRANT OPTION — имеющиеся привилегии соответствующего уровня.
SHOW GRANTS ... USING раскрывает права роли для пользователя. mysql.user содержит глобальные флаги и данные аккаунта; N в глобальном Select_priv не запрещает SELECT, полученный на таблицу через роль. mysql.role_edges хранит назначения, mysql.default_roles — настройки ролей по умолчанию.
REVOKE снимает указанные права; блокировка ACCOUNT LOCK запрещает вход, но не стирает выдачу привилегий. PASSWORD EXPIRE требует смены пароля при допустимом входе и тоже не является отзывом прав. Изменения аккаунтов не отменяются ROLLBACK. FLUSH PRIVILEGES после CREATE USER/GRANT/REVOKE не нужен; для Workbench нужно обновить отображение интерфейса.
Данные через INSERT можно проверить в транзакции и отменить ROLLBACK. Ранее созданные триггеры при этом продолжают действовать. Отказ привилегий 1142 проверяется раньше изменения строки; отказ триггера 1644 относится к нарушению правила предметной области.
